Docker: a "computer" that is really just a fenced-off process

A teammate sends you an app and says "just run the container." A second later it is running, with its own files, its own network and exactly the software versions it needs, on your laptop. It feels like a tiny virtual computer, but it starts almost instantly. The design challenge: how do you give a program its own private world without paying for a whole second operating system?

Legend: terms used below
Kernel
The core of the operating system. It talks to the hardware and decides which program gets the CPU, memory and files.
Container
An ordinary running program that the kernel has been told to isolate from everything else on the machine.
Namespace
A Linux feature that gives a program its own private view of something, such as the list of running programs, the network or the file system.
Cgroup
A Linux feature that puts a cap on how much CPU and memory a group of programs may use.
Image
The packed-up files a container starts from: the app plus the libraries and tools it needs.
Layer
One step of an image, holding only the files that changed in that step. Layers are stacked to form the full set of files.
Virtual machine
A pretend computer, with its own full operating system, running on top of a real one.

The design

A container is not a small computer. It is a normal program running on your normal kernel, with two kinds of fences put around it.

The first fence controls what it can see. Linux namespaces let the kernel show a program a filtered version of the machine. Inside the container, the app thinks it is the only program running, has its own network address, and sees its own file system as the whole disk. The same machine can show a different view to every container.

The second fence controls what it can use. Cgroups set limits, so one container that goes wild cannot eat all the memory and starve its neighbours.

The other half of Docker is how the files get there. A container starts from an image, and an image is built from stacked layers. One layer might be a base set of system files, the next adds a language runtime, the next adds your app. Each layer stores only what changed.

Because layers are read-only and shared, ten containers from the same image do not copy the files ten times. They all read the same layers, and each gets a thin writable layer on top for its own changes. Edit a file and only that one file is copied up into your private layer.

Why

The older way to isolate software was a virtual machine: a whole pretend computer, each with its own kernel. That gives very strong separation, but every one carries a full operating system, so it is heavy and slow to boot.

Containers trade some of that separation for speed. Since they share the host's kernel, starting one is just starting a program. The cost is that a bug in the shared kernel can matter to every container, and a Linux container needs a Linux kernel underneath. That is the real trade-off: lightweight and fast, versus a thicker wall.

A container is not a smaller computer. It is a normal program that has been told what it may see and use.
Confidence note

I am confident in the namespace, cgroup and layered-file-system picture; it is how Docker and similar tools work on Linux. Details vary between tools and versions (for example which file-system driver stores layers), and I did not re-fetch sources in this run.

Things this explains

  1. Containers start in about a blink, while virtual machines take a while. There is no operating system to boot, just a program to launch inside its fences.
  2. "Works on my machine" mostly goes away. The image carries the exact libraries and tools the app was tested with, so the container sees the same files everywhere.
  3. Docker on a Mac or Windows laptop quietly runs a small Linux virtual machine. Containers need a Linux kernel to share, so those systems bring one along.

Sources: Linux kernel documentation on namespaces and control groups, and Docker's documentation on images and layers. Written from background knowledge; not re-fetched this run.

Google Maps: the fastest route is a moving target

You ask for directions across a city and get an answer in a blink, along with an arrival time that is usually right. But the "best" route depends on traffic that is changing right now, and the road network has millions of possible paths. The design challenge: how do you search that huge maze quickly, with costs that keep shifting?

Legend: terms used below
Graph
A map reduced to dots and lines. Dots are junctions, lines are the road pieces between them.
Shortest-path search
A method for finding the cheapest way from one dot to another in a graph, where "cheapest" can mean least time.
Road segment
One stretch of road between two junctions, treated as a single unit with its own travel time.
Shortcut
A precomputed jump that skips over many small roads, such as "from this town to that one, via the highway".
Machine-learning model
A program that learns patterns from past examples, here from past traffic, and uses them to make predictions.

The design

Imagine asking a friend the quickest way to the airport. They would not think about every street in the country. They would think: get to the highway, stay on it, then take the airport exit. Maps software does the same, in two steps.

First, the road network is turned into a graph. Each road segment gets a cost, usually its predicted travel time. Finding a route then becomes a shortest-path search.

Second, the search is helped by work done ahead of time. Big roads are the ones almost every long trip uses, so the system can prepare shortcuts between important junctions in advance. When you ask for a route, the search only crawls through small streets near your start and end, and leaps across the middle using the shortcuts.

The arrival time is its own problem. A road that is jammed now may be clear by the time you reach it. So Google's research team has described using a machine-learning model that looks at current speeds and at how traffic on neighbouring roads usually behaves, to predict what each segment will be like when you get there, not just what it is like now.

Why

A plain search that crawls every road is far too slow for a whole country, and it would have to be redone for every user. Shortcuts move most of the work to before you ask. The price is that shortcuts are built for one set of costs. If a road's time changes a lot, the shortcuts that rely on it can go stale.

That tension is the heart of it: precomputing makes answers instant, while live traffic makes precomputed answers wrong. Real systems balance the two, keeping the preparation based on stable things like road layout and speed limits, and layering live conditions on top.

Do the slow thinking before you are asked, then adjust for what is happening now.
Confidence note

Google has not published its exact routing method. The shortcut idea is a well-known technique from research on route planning, and I am confident it is the general family, but I cannot say precisely what Google runs today. The traffic-prediction model comes from Google's own research writing. I did not re-fetch sources in this run.

Things this explains

  1. Directions come back almost instantly, even for a trip across the country. The search only works hard near the start and end; the middle is covered by precomputed shortcuts.
  2. Maps can reroute you mid-drive when a crash happens ahead. New speed reports change the cost of those segments, and the search runs again with the updated costs.
  3. The arrival time sometimes changes even though you are on the same road. The estimate is a prediction about roads still ahead, and it gets revised as conditions shift.

Sources: Google DeepMind's blog post on traffic prediction with graph neural networks, and academic work on route planning with precomputed shortcuts (contraction hierarchies). Written from background knowledge; not re-fetched this run.

DNS: a phone book nobody owns

Every time you open a website, your device first has to turn a name like example.com into a numeric address. Billions of devices do this all day, and no single computer holds the whole list. The design challenge: how do you answer that question fast, for everyone, with no central owner?

Legend: terms used below
IP address
The number that identifies a machine on the internet. Computers use these, not names, to reach each other.
DNS
The Domain Name System. The shared system that turns names into IP addresses.
Resolver
A helper server, usually run by your internet provider or a company like Google or Cloudflare, that does the looking-up on your behalf.
Cache
A saved copy of an earlier answer, kept so the same question does not have to be asked again.
TTL
"Time to live". A number attached to an answer saying how long others may keep their saved copy before asking again.
UDP
A simple way to send small messages over the internet: fire it off, no handshake first, no promise it arrives.

The design

When you type example.com, your device needs its IP address. Your device does not go hunting for it. It asks a resolver, and the resolver does the work.

The names in DNS are organised like a tree, read right to left. The resolver starts at the top, at the root servers, and asks who handles .com. A .com server then says who handles example.com. Finally that server, the one the site owner chose, gives the actual address.

Each step only points to the next one. No server knows everything, and each one knows only its own slice. That is what lets the system have no central owner: whoever owns a name controls the answers for it.

That walk would be slow if it happened every time, so the second half of the design is caching. The resolver remembers answers. If thousands of people on the same provider look up the same popular site, only the first one triggers the walk. Everyone else gets the saved copy straight away.

Each answer comes with a TTL, chosen by the site owner, that says how long the saved copy is allowed to live. Your own device and browser keep a cache too.

Why

Early on, the internet's name list was one file that everyone downloaded from one place. That broke as the network grew: one machine could not serve everybody, and one organisation could not approve every change. DNS was designed to spread both the load and the control around.

The trade-off is that you can never be sure an answer is up to date. Caching makes lookups fast, but a cached answer can be stale until its TTL runs out. Site owners pick the TTL: short means changes spread quickly but more lookups; long means fewer lookups but slower changes.

This is also why DNS questions traditionally travel over UDP. A question and its answer are each tiny, so a full connection handshake would cost more than the lookup itself. If an answer is too big for one small message, the lookup falls back to a more careful connection.

No one server knows the answer. Everyone knows who to ask next.
Confidence note

This is the classic picture. Real lookups have extras I have skipped: many copies of each server, security signatures, and newer encrypted ways of asking (such as DNS over HTTPS) that do not use plain UDP. I also did not fetch sources during this run, so treat the details as a starting point.

Things this explains

  1. A site you just moved can look broken for some people but not others. Different resolvers hold old saved answers until their TTL runs out.
  2. Switching your DNS provider can make browsing feel snappier. A busy resolver is more likely to already have the answer cached, so it skips the walk.
  3. When DNS has an outage, it feels like "the internet is down" even though servers are fine. Without the lookup you have no address to connect to, so nothing starts.

Sources: RFC 1034 and RFC 1035 (the original DNS specifications), and Cloudflare's learning pages on DNS. Written from background knowledge; not re-fetched this run.

Node.js: one worker, thousands of waiting customers

A chat server or API might have ten thousand people connected at once, and most of them are doing nothing at any given moment. The design challenge: how do you serve all of them without paying for ten thousand threads that mostly sit idle?

Legend: terms used below
Thread
One line of work running inside a program. A program can have many threads running at the same time, but each one costs memory and switching between them costs time.
Blocking
When a thread has to stop and wait for something slow, like a disk read or a reply from another server, and can do nothing else meanwhile.
Event loop
A loop that keeps asking "has anything finished yet?" and, when something has, runs the code that was waiting for it.
Callback
A function you hand over saying "run this when the slow thing is done".
Operating system (OS)
The software that manages the computer. It handles the network card and the disk, and can tell a program when data has arrived.
libuv
The library inside Node.js that runs the event loop and talks to the operating system.

The design

Think about what a web server actually does for one request. It reads a little data, asks a database a question, waits, gets an answer, and sends a reply. Nearly all of the time is waiting. The server's own work takes a tiny slice.

The classic approach gives every connection its own thread. When that thread hits a slow step it is blocked, and the other threads carry on. It works, but ten thousand mostly-asleep threads eat a lot of memory.

Node.js does something different. It runs your JavaScript on one thread, and that thread never waits. When your code says "read this file" or "query this database", Node hands the job to the operating system, along with a callback, and moves on to the next piece of work.

Running underneath is the event loop, built into a library called libuv. It keeps asking the OS "did anything finish?". When a network reply has arrived, it takes the matching callback and runs it on the main thread.

One detail worth knowing: not everything is handed to the OS in the same way. Network connections can be watched efficiently by the OS itself. Some other jobs, like many file operations, are run on a small pool of helper threads that Node keeps behind the scenes. Your own JavaScript still stays on the single main thread either way.

Why

The constraint is that waiting is cheap for the machine but expensive for a thread. A thread reserves memory and has to be scheduled, even when it is asleep. For a program that is mostly waiting on other things, such as a chat server or an API that calls other APIs, that is a lot of overhead for nothing.

The trade-off is sharp. Because there is only one JavaScript thread, a slow calculation blocks everyone. If one request spends two seconds crunching numbers, every other connection freezes for those two seconds, since nobody else can get a turn. Node is great at waiting and poor at heavy computing, unless you push that work to separate worker threads or other services.

Don't make a thread wait. Tell the OS what you're waiting for, and keep going.
Confidence note

This is the simplified picture. The real loop has several phases (timers, I/O, scheduled follow-ups and more) that decide the order callbacks run in, and I have not covered those. The default size of the helper thread pool and exactly which operations use it are details I'm recalling from memory, so check the Node docs before relying on them.

Things this explains

  1. A tiny Node server can hold a huge number of open connections. Idle connections cost almost nothing because no thread is sitting on each one.
  2. One heavy loop can make a whole server unresponsive. All callbacks share one thread, so a long calculation delays every other request in line.
  3. You see callbacks, promises and async everywhere in Node code. They are how you say "carry on with this when the slow thing is done" instead of stopping to wait.

Sources: the Node.js docs page The Node.js Event Loop and the libuv documentation. Written from background knowledge without re-fetching during this run; treat as starting points.

Shazam: naming a song from ten noisy seconds

You hold your phone up in a loud cafe and a few seconds later it names the song. The design challenge: your recording is full of chatter and clinking cups, it starts at a random moment, and the app has to find a match among tens of millions of tracks almost instantly.

Legend: terms used below
Audio fingerprint
A small, compact summary of a piece of audio that stays the same even when the audio is noisy or quiet. It is not the sound itself.
Frequency
How high or low a sound is. A bass note is a low frequency and a cymbal is a high one.
Spectrogram
A picture of a sound with time going left to right and frequency going bottom to top. Brighter spots mean louder.
Peak
A spot on the spectrogram that is louder than everything around it.
Hash
A short code computed from some data. The same data always gives the same code, so codes can be looked up quickly.
Index
A lookup table built ahead of time, so you can jump straight to the entries you want instead of scanning everything.

The design

The obvious idea is to compare your recording against every song, wave against wave. That fails right away. Your clip has background noise, the phone microphone squashes the sound, and you started recording mid-song.

Shazam's approach, described in a 2003 paper by one of its founders, is to throw most of the sound away. First the app turns the clip into a spectrogram. Then it keeps only the peaks, the loudest spots in each small patch of time and frequency. What remains looks like a scatter of dots, like stars on a night sky.

Loud spots are a good thing to keep because they tend to survive noise. A chatty cafe can drown out quiet details, but the strongest notes of the song still poke through.

Single dots are not distinctive enough, since many songs share a loud note. So the app links dots in pairs: one dot, plus a few nearby dots that come just after it. Each pair becomes a small code made from the two frequencies and the time gap between them. That code is the audio fingerprint, or really a bag of hundreds of them.

On the server side, every known song went through the same process ahead of time, and all its codes were stored in a giant index, keyed by the code. Each stored entry also remembers which song it came from and when in the song it happened.

When your codes arrive, each one is looked up and returns a list of songs that contain it. Many are coincidences. The trick is timing. If your clip really is from song X, then the codes line up: every match sits at the same offset, say "your clip starts 73 seconds into the song". Coincidences scatter all over the place. The song with the most matches agreeing on one offset wins.

Why

This design is shaped by two limits: noise and scale. Keeping only peaks makes the fingerprint tolerant of noise. Using pairs of peaks makes each code specific enough that a lookup returns a short list instead of half the catalogue. And because each lookup is a direct jump into the index, the work does not grow with the number of songs the way a scan would.

The trade-off is what it cannot do. Fingerprints identify one specific recording. A live version, a cover, or you humming the tune has different peaks and timings, so it will not match. That is a different, harder problem.

Don't compare the sound. Compare a few loud landmarks and when they happen.
Confidence note

This follows the published 2003 algorithm. Shazam has surely changed it since, and I don't know the current details such as how its index is stored or how many codes are used. Where the matching happens in the app today (phone versus server) can also differ by feature.

Things this explains

  1. It works when you start mid-song. Codes are matched by their gap to each other, not by where your clip began.
  2. It can work in a loud room but not for a cover. Loud peaks survive noise, yet a different performance has different peaks.
  3. Results come back fast. Only compact codes are sent, and each is a direct lookup instead of a scan over the catalogue.

Sources: Avery Wang, "An Industrial-Strength Audio Search Algorithm" (ISMIR 2003). Written from background knowledge without re-fetching during this run; treat as a starting point.

One address, hundreds of buildings: Cloudflare's anycast

Cloudflare sits in front of a huge share of the web, soaking up traffic and attacks. The design challenge: every visitor needs to reach a nearby machine, and if a building goes dark or a flood of junk traffic arrives, nobody should notice. And ideally nobody has to decide where each visitor goes.

Legend: terms used below
Anycast
Many machines in many places all claim the same IP address, and each visitor gets sent to whichever one is closest in network terms.
IP address
The number that identifies a machine on the internet, a bit like a phone number.
Data center
A warehouse full of servers with fast internet connections. Cloudflare has them in hundreds of cities.
BGP
The way networks tell each other "you can reach this address through me". It is how the internet's routers learn the map.
Router
A machine whose job is to pass internet traffic along, one hop at a time, toward its destination.
DDoS attack
Someone aims a flood of fake traffic at a site to knock it over.

The design

Picture a pizza chain with one phone number. You dial it and the phone network connects you to the shop nearest your house. You never pick a shop, and the chain never needs to know where you live.

That is anycast. Normally an IP address belongs to one place. With anycast, Cloudflare's data centers all around the world announce the same address at the same time. They do it using BGP, the system networks use to tell each other which addresses they can deliver to.

Every router on the way picks the best path it knows. So a visitor in Mumbai tends to end up at a Mumbai building and one in Paris at a Paris building, with no special logic and no lookup table of users.

Failure handling comes almost for free. If a data center goes dark, it stops announcing the address. Routers elsewhere forget that path, and traffic that used to land there quietly slides to the next-nearest building.

Why

The obvious alternative is to make the website's name point at a different address per region, and have a smart system hand out the right one. That works, but it is slow to react: those answers get remembered by phones and browsers, so a bad answer lingers.

Anycast also helps against a DDoS attack. Attackers are spread across the world, so each building only receives the slice of the flood that is near it, instead of one site taking all of it. The trade-off: "closest" means closest on the network map, which is not always closest on the real one, and if routes shift in the middle of a long conversation, that conversation can land on a different machine and break. Operators put real work into making that rare.

Nobody sends you to the nearest building. The internet's routing just does it.
Confidence note

This is the simplified picture. Cloudflare has described using more than plain anycast, for example extra layers to spread work among machines inside each building, and I haven't verified the current details of how it does that. I also haven't covered how it treats different customers' traffic differently.

Things this explains

  1. Public DNS like 1.1.1.1 is easy to remember. One short address works worldwide, because every location answers to it.
  2. Big sites survive outages you never hear about. A failed building just stops announcing itself and traffic flows around it.
  3. Attacks rarely take a whole network down. The flood is chopped up by geography before it reaches any single machine.

Sources: Cloudflare's anycast explainer and engineering blog posts tagged anycast. Written from background knowledge without re-fetching during this run; treat as starting points.

Git is a filing cabinet that names things by their contents

Millions of developers use Git to save every version of their code, jump back in time, and work on separate copies without stepping on each other. The design challenge: keep the full history of a huge project, cheaply, and notice instantly if anything was ever tampered with or corrupted.

Legend: terms used below
Hash
A short fingerprint computed from some data. The same data always gives the same fingerprint, and even a one-letter change gives a completely different one.
Content-addressable
Stored and looked up by a fingerprint of the content itself, instead of by a name you picked.
Commit
One saved snapshot of the whole project, plus a note about who saved it, when and why.
Branch
A movable label that points at one commit. Making a new one just means adding a label.
Delta
Storing only what changed between two versions, not a full copy of each.

The design

Imagine a filing cabinet where you never choose a label. Instead, a clerk reads each document, works out its hash, and files it under that fingerprint. Ask for the fingerprint, get the exact document back. That is Git's core: a content-addressable store.

Everything is built from just a few kinds of items filed this way. A file's contents. A folder, which is a list of names pointing at file fingerprints. And a commit, which points at the top folder and at the previous commit.

Notice the trick: a commit's fingerprint depends on the fingerprints inside it, including its parent's. So the history is a chain where each link vouches for everything before it. Change one old file and every fingerprint after it changes too.

Does saving a full snapshot every time eat your disk? No, because of the filing rule. If a file didn't change, its fingerprint didn't change, so the new snapshot simply points at the copy already in the cabinet. Only edited files add anything new.

A branch is then almost free. It is a sticky note with a commit's fingerprint on it. Creating one writes a tiny note; no files are copied. Committing just moves the note forward.

Why

Git was built for the Linux kernel, a project with thousands of contributors working at once and no central server they all had to trust. Naming things by their contents means any copy can check itself: if the fingerprints match, the data is right. That is what lets everybody hold a full copy of the history and still agree.

The trade-off is that history is permanent by design. You can't quietly edit the past; "rewriting" it really means making new commits with new fingerprints. Also, storing whole snapshots would grow large over time, so Git periodically packs its files and keeps only the deltas between similar ones. You get snapshot thinking with delta-sized disk use.

Git doesn't track changes. It stores snapshots, and works out the changes when you ask.
Confidence note

This is the simplified picture. Real Git has a few more item types (such as tags), and the hash function it uses is in the middle of a long migration to a newer one. I haven't covered those details, and I haven't checked how any specific hosting site stores repositories on its servers.

Things this explains

  1. Creating a branch feels instant. It is one tiny label, not a copy of your project.
  2. Those long random-looking commit IDs. They are the fingerprints, and they are the commit's real name.
  3. "Rewriting history" breaks teammates' copies. A rewritten commit has a new fingerprint, so everyone else's copy suddenly disagrees about what the past was.

Sources: Pro Git book, Git Objects and Packfiles; Branches in a Nutshell.

A whole database in one file: SQLite

Your phone's contacts, your browser's history and countless apps all keep their data in a real database, yet none of them runs a database server. SQLite is a database that is just a library and a file. The design challenge: stay correct even when the power dies in the middle of a save.

Legend: terms used below
Database server
A separate program that owns the data. Other programs connect to it over a network and ask it to read or change things. Postgres and MySQL work this way.
Library
Code that gets built into your own program, so it runs inside it and not as a separate program.
Page
A fixed-size chunk of the file. The database reads and writes the file one page at a time.
Transaction
A group of changes that must happen all together or not at all, like moving money between two accounts.
Journal
A safety copy kept on the side while changes are being made, so a crash can be undone cleanly.
WAL (write-ahead log)
A mode where new changes are first added to the end of a separate log file, and only copied into the main file later.
Checkpoint
The moment the log's changes are copied into the main database file and the log is cleared.

The design

Most databases work like a restaurant. You sit at a table (your app), and a kitchen (the database server) does the cooking. SQLite is more like a cookbook on your own shelf. You read it and cook right there in your own kitchen.

Technically, SQLite is a library. When your app asks a question in SQL, the code runs inside your app's own process and reads one ordinary file on disk. No network, no setup, no password. Copying the database means copying the file.

Inside that file, the data is cut into equal-sized pages, and each table is organised as a tree of pages, so looking something up means hopping down a few levels instead of reading everything.

That raises the hard question. If your app writes straight into the file, what happens when the phone dies halfway through saving? You could be left with half-old, half-new data.

SQLite's answer is the transaction. Before changing a page, it first saves a safety copy in a journal. If the power dies, the next program to open the file sees the leftover journal and rolls the file back to how it was. A save either fully happened or never did.

Modern setups often use a different trick, called WAL mode. Instead of copying old pages aside, new changes are simply added to the end of a log file. Readers look at the main file plus the log, so a writer never blocks them. Now and then a checkpoint tidies the log into the main file.

Why

The big trade-off is who gets to write. With one file and no middleman, nobody is there to direct traffic, so SQLite allows only one writer at a time. Others wait their turn. Many readers are fine, but writers queue.

That sounds like a weakness, and for a website with thousands of people saving at once, it is. But most uses are one app, one user, one phone. There, giving up the server buys a lot: nothing to install, nothing to keep running, nothing to secure, and a file you can copy or back up like a photo.

The best database server is the one you never have to run.
Confidence note

This is the simplified picture from SQLite's own documentation. Details vary by setup: the default is the rollback journal, and WAL mode has to be switched on. I haven't checked how any specific app, phone or browser configures it, so don't read this as a claim about them.

Things this explains

  1. Apps recover fine after a crash or dead battery. The leftover journal or log tells SQLite how to roll back the half-finished save the next time the file opens.
  2. Backing up an app's data can be as easy as copying one file. The whole database lives in it. (Copy it while nobody is writing, or use SQLite's backup tool, to avoid grabbing a half-finished state.)
  3. It's a poor fit for a busy multi-user website. Writers queue behind one another, and sharing a database file across a network is risky. That's what database servers are for.

Sources: SQLite documentation, Appropriate Uses For SQLite; Atomic Commit In SQLite; Write-Ahead Logging; Database File Format.

One message, 200,000 readers: inside Discord

Imagine a group chat with 200,000 people. Someone says "hi" and every phone lights up almost instantly. Discord also remembers every message ever sent and can find any of them when you scroll back. It manages both with one simple idea: split the work up so no single worker ever gets overwhelmed.

Legend: terms used below
Server (guild)
What Discord calls a community. Each one has channels like #general. Discord's code calls it a "guild".
WebSocket
A connection between your app and Discord's computers that stays open, so Discord can push a message to you the moment it arrives instead of waiting for you to ask.
Process
A tiny worker inside a program that does one job and talks to other workers by sending messages. Discord's system runs millions of these at once.
Elixir / Erlang
Programming languages built for running huge numbers of these tiny workers. Discord's live chat system is written in Elixir, which runs on Erlang's engine.
Node
One machine (or one copy of the program) in a cluster of many machines working together.
Fan-out
Taking one message and delivering a copy to many recipients.
Partition
A slice of a database stored together. Splitting data into partitions lets many machines share the work.
Hot partition
A slice that gets far more traffic than the others, like one checkout lane with a huge queue while the rest sit empty.
Request coalescing
When many people ask for the same thing at the same moment, do the work once and share the answer.
p99 latency
How slow the slowest 1 in 100 requests is. It shows what unlucky users experience, not just the average.

The design

First, the live part. When you open Discord, your app keeps a WebSocket open to Discord's computers. Every connection gets its own tiny worker (a process), and every server gets one too. Think of it as a switchboard operator for that community. Send a message and it goes to the operator, who passes it on to everyone who is online. All of this runs on Elixir, a language made for exactly this kind of job.

The obvious approach is for the operator to send copies one at a time. That's fine for ten friends. For a giant server it's a traffic jam, because the operator can only do one hand-off at a time. Discord's answer: the operator sends just one copy to each machine (a node), and a helper on that machine passes it to the people connected there. It's still fan-out, but the work is shared between many workers.

Now the remembering part. Messages are stored like papers in a filing cabinet: one folder for each channel and stretch of time, with the messages inside kept in order. Every message ID includes the time it was sent, so "show me the latest messages" just means opening the right folder and reading the end.

In front of the database sits a helper layer called the data services. Picture a librarian who gets asked the same question by a big crowd. They look it up once and read the answer out to everyone. That's request coalescing. It works because all questions about one channel go to the same librarian.

Why

Both ideas exist because a few servers are far bigger than the rest.

The old live system did fine for small servers but struggled with big ones. Discord once measured a server with about 30,000 people online where a single message took up to two seconds to reach everyone. The operator was doing tens of thousands of tiny hand-offs in a row, and they added up. Sending one copy per machine spread that work out.

The database had a similar problem. A few very busy channels (hot partitions) got hammered while thousands of quiet ones sat idle, and the database sometimes paused to clean up after itself. Discord switched databases and added the librarian layer. It now runs on 72 machines instead of 177, and even the slowest 1% of requests (the p99 latency) got several times faster.

A send is cheap. Thirty thousand sends from one process is a queue.
Confidence note

These figures come from Discord's own engineering blog posts (2017 and 2023), so they show how things worked then, and Discord has likely changed things since. I couldn't confirm the exact order of steps between the app, the database and the live system when you hit send, so the first diagram shows the general idea rather than an exact trace. The "stretch of time" per folder was about ten days in older posts. Treat that as approximate.

Things this explains

  1. Big servers only show part of the member list. Updating all 200,000 names for everyone would cause the same traffic jam, so you only get updates for the names on your screen.
  2. Jumping to an old message is fast. Message IDs include the time, so Discord knows which folder to open. (This is my own reasoning from how the storage works, not something Discord says directly.)
  3. An @everyone ping doesn't break things. Thousands of people open the channel at once and ask for the same recent messages. The librarian answers once for all of them.
